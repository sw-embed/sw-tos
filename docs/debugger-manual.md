# SWTOS Debugger Manual

The Debugger pane of the [Windows frontend](windows-usage.md) accepts
host-side commands rather than SWTOS TTY input. Focus it with `Ctrl-A 3`,
type a command, and press Enter. `help` prints the one-line summary that this
manual expands.

## Two kinds of command

The distinction explains most surprises:

- **Map commands** answer from `program.debug.json`, the debug map built
  alongside the image. They involve no target round trip, work while the
  target is running or stopped, and describe the program *as built*:
  `sym`, `list`, `dis`.
- **Target commands** send a request frame and print whatever the target
  replies. They describe the machine *as it is running right now*:
  `regs`, `x`, `bt`, `pause`, `continue`, `step`, `next`, `break`, `bl`,
  `delete`, `kill`, `detach`.

Map commands require the target's build identity to match the loaded map.
Until the target reports it you get `target build identity not received`; on a
mismatch the map is refused rather than trusted. A matching build prints
`build matched crc24:<id>` when the frontend connects.

## Locations: `LOC`

Uppercase words in the help line are argument placeholders, not commands.
There is no `loc` command. `LOC` accepts three forms, tried in this order:

| Form | Example | Meaning |
|------|---------|---------|
| Hex address | `dis 005581`, `dis 0x5581` | A 24-bit address; `0x` optional, max `ffffff` |
| Symbol name | `dis counter` | Resolved through the map's symbol table |
| Source line | `dis app.s:4140` | The first instruction generated by that source line |

`x` is the exception: it takes a raw `ADDR` only and does **not** resolve
symbols or source lines. Use `sym NAME` first, then pass the address it
prints.

## `list` versus `dis`

Both take a `LOC`, and they are easy to confuse:

- `list LOC` prints **one line**: the source position of the instruction at
  or immediately below the address, as `ADDRESS source.s:LINE TEXT`. It
  searches backwards, so an address in the middle of an instruction still
  resolves. Use it to answer "what source produced this address?"
- `dis LOC [N]` **disassembles**: it prints up to `N` instructions from the
  address *forward*, each as `ADDRESS BYTES TEXT`. `N` defaults to 8 and is
  capped at 32. Use it to read the code around a location.

```text
list counter
000010 app.s:7 lc r0,1

dis counter 3
000010 4401     lc r0,1
000012 28       jmp (r2)
```

An address with no instructions at or after it reports
`no instructions at <address>` rather than printing nothing. This matters
because the addresses you paste in usually come from `regs`, which reports a
stale program counter for an endpoint that has already exited -- an address
far outside the image is the normal symptom of a dead endpoint, not a broken
command.

## `x ADDR [N]` -- examine memory

Reads live target memory and prints it as hex bytes:

```text
x 000000 4
000000: 29 00 ec fe
```

`N` defaults to 12 and must be **1 to 12** -- one frame's worth. Larger
requests are refused with
`memory request requires a 24-bit address and 1..12 bytes`. Unlike `dis`,
which shows what was built, `x` shows what is in memory now, so it is the way
to inspect data the program has written.

## Command reference

| Command | Kind | Effect |
|---------|------|--------|
| `help` | -- | Print the command summary. An empty line does the same |
| `sym NAME` | map | Print `NAME = ADDRESS (module)` |
| `list LOC` | map | Print the source line at or below `LOC` |
| `dis LOC [N]` | map | Disassemble `N` instructions from `LOC` (default 8, max 32) |
| `regs [EP]` | target | Registers for endpoint `EP` (default 1): `r0 r1 r2 sp`, then `pc status` |
| `x ADDR [N]` | target | Read `N` bytes (1..12, default 12) of live memory at `ADDR` |
| `bt` | target | Best-effort ABI backtrace from the saved frame pointer chain |
| `break LOC`, `b LOC` | target | Set an instruction breakpoint |
| `delete LOC` | target | Remove the breakpoint at `LOC` |
| `bl` | target | List breakpoints, naming the enclosing function where known |
| `pause` | target | Stop the emulator |
| `continue`, `c` | target | Resume the emulator |
| `step`, `s` | target | Execute one instruction |
| `next`, `n` | target | Execute one instruction, stepping over a call |
| `kill EP` | target | Request safe termination of endpoint `EP` |
| `detach` | target | Detach the adapter and exit |

Anything else prints `unknown debugger command; use help`.

## Endpoints

`EP` is a scheduler endpoint, the same number the Resources pane shows as
`ep=`. Endpoint 1 is the shell. `regs EP` returns a coherent interrupted
frame for a runway-saved process and does not itself preempt it; run it twice
with heartbeats in between to watch a saved `r0` change across
resume/preemption cycles.

`kill EP` queues termination of a certified hostile process parked at a safe
interrupt context. SWTOS reclaims only a complete parked context, through the
ordinary task-exit path, after which Resources omits the endpoint. The reply
is `kill requested for endpoint EP`, or
`cannot kill endpoint EP: status N` when the process is not quiescent.

## Emulator and hardware

`regs`, `x`, `bt`, and `kill` are read-only or scheduler-mediated operations
that behave identically on the emulator and on the physical COR24-TB.

`break`, `delete`, `bl`, `pause`, `continue`, `step`, and `next` are provided
by the emulator-backed adapter. Arbitrary instruction breakpoints are **not**
supported on the physical board.

## Stop reasons

`pause`, `step`, `next`, and a breakpoint hit report the reason and program
counter, for example `breakpoint at 000010`. The reasons are `breakpoint`,
`paused`, `running`, `halted`, `invalid instruction`, `stack overflow`, and
`stack underflow`.
